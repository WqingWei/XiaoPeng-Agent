## 1. 项目概述

### 1.1 项目定位

打造一位 **"小鹏 AI 出行服务管家"**——一个基于大语言模型的智能服务编排 Agent。该 Agent 不重复实现语音识别、底层车控或自动驾驶算法，而是在**已有的座舱能力与 Robotaxi 服务能力之上**，充当"中枢大脑"角色：

- **读懂意图**：理解用户自然语言背后的真实需求（包括未说出口的需求）
- **编排服务**：组合调度空调、座椅、导航、补能、订单管理等一整套服务工具
- **守住底线**：在疲劳驾驶、儿童安全、乘客求助等关键时刻，做出正确的安全决策

### 1.2 核心设计哲学

| 原则 | 说明 |
|------|------|
| **意图优先** | 不机械执行表面指令，要洞察真实需求 |
| **编排为王** | 价值在于工具组合的方式，而非工具本身 |
| **安全第一** | 宁可拒绝执行，也不突破安全边界 |
| **可解释性** | 每个决策都要给出理由，让用户和评委理解 |
| **温度沟通** | 输出自然、有温度的语言，而非冰冷的机器指令 |

## 2. 用户角色与使用模式

### 2.1 用户角色定义

| 角色 | 描述 | 典型场景 |
|------|------|---------|
| **车主（Owner）** | 车辆拥有者，自驾出行 | 日常通勤、长途自驾、接送家人 |
| **乘客（Passenger）** | Robotaxi 乘客，非车主 | 打车出行、无人出租车 |
| **远程安全员（Operator）** | Robotaxi 远程监控人员 | 异常接管、紧急情况处理 |

### 2.2 两种运行模式

```
┌─────────────────────────────────────────────┐
│            小鹏 AI 出行服务管家               │
├──────────────────┬──────────────────────────┤
│   车主自驾模式    │    Robotaxi 乘客服务模式   │
│  (Owner Mode)    │   (Robotaxi Mode)        │
├──────────────────┼──────────────────────────┤
│ • 车主本人交互    │ • 乘客通过App/车机交互     │
│ • 座舱控制为主    │ • 订单管理 + 行程服务为主  │
│ • 驾驶安全辅助    │ • 乘客安全与体验保障      │
│ • 个性化偏好记忆  │ • 标准化服务 + 异常处理    │
└──────────────────┴──────────────────────────┘
```

## 3. 五大核心能力需求

### 3.1 场景理解能力

**定义**：从用户输入（自然语言、车辆状态、环境事件）中准确识别真实需求的能力。

#### 3.1.1 需求分层模型

```
用户输入层
  ├── 显性需求（Explicit）：用户直接说出的请求
  │     例："帮我打开空调" → 开空调
  │
  ├── 隐性需求（Implicit）：需要推理得出的需求
  │     例："我有点困" → 疲劳风险评估 → 综合干预方案
  │
  └── 紧急需求（Urgent）：安全相关的即时需求
        例："孩子好像在发烧" → 儿童健康紧急响应
```

#### 3.1.2 意图识别要求

| 维度 | 要求 | 示例 |
|------|------|------|
| 上下文感知 | 结合当前车速、位置、时间、天气等判断 | 高速行驶中说"有点冷"→ 不能开窗，调高空调温度 |
| 多轮对话 | 支持追问和澄清，不一次假设过多 | "附近有什么" → 追问"您是想找充电站还是餐厅？" |
| 情绪感知 | 识别用户焦虑、疲惫、愤怒等情绪 | 用户语气急促+"怎么还没到" → 安抚 + 实时ETA |
| 乘客区分 | 区分车主本人 vs 后排乘客/儿童的需求 | 后排说"好热" → 调整后排空调，而非全车 |

### 3.2 服务编排能力

**定义**：基于已有工具箱，组合多个原子服务形成完整服务闭环的能力。

#### 3.2.1 编排原则

- **原子化**：每个工具调用是独立的原子操作
- **有序性**：工具调用有明确的先后顺序和依赖关系
- **并发性**：无依赖的工具可以并发执行
- **幂等性**：重复调用同一工具不会产生副作用
- **回滚性**：某一步失败时，能回滚或给出降级方案

#### 3.2.2 编排模式

| 模式 | 说明 | 示例场景 |
|------|------|---------|
| 串行编排 | A → B → C，依次执行 | 导航到充电站 → 到达后降下车窗 → 开始充电 |
| 并行编排 | A + B + C，同时执行 | 同时调空调 + 调座椅 + 播放音乐 |
| 条件编排 | if X then A else B | 如果电量<20%则推荐充电站，否则继续导航 |
| 循环编排 | 持续监测，周期性执行 | 持续监测疲劳指标，每5分钟评估一次 |
| 降级编排 | A失败 → 降级到B | 自动泊车失败 → 提示手动泊车 + 提供指引 |

### 3.3 安全边界能力

**定义**：识别高风险场景，在必要时拒绝执行、发出警告或转交人工的能力。

#### 3.3.1 安全等级定义

```
  等级        名称           Agent行为             示例
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  L0        安全(Safe)      正常执行              "帮我放首歌"
  L1        注意(Caution)   执行+提醒             "我想在路边停一下"（非停车区）
  L2        警告(Warning)   拒绝+替代方案          "我有点困"（拒绝继续驾驶建议）
  L3        危险(Danger)    强制干预+转人工         儿童独自在车内+车辆启动
  L4        紧急(Emergency) 立即停车+紧急联络       乘客突发疾病/事故
```

#### 3.3.2 安全规则要求

- **硬规则（不可违反）**：
  - 行驶中禁止操作需要驾驶员视觉/手动关注的功能
  - 儿童安全锁启用时禁止从车内开门
  - 驾驶员疲劳等级≥L2时强制建议休息
  - 乘客求助信号必须立即响应

- **软规则（可酌情调整）**：
  - 空调温度建议范围 18-28°C（用户明确要求时可适当放宽）
  - 充电站推荐优先选小鹏自营站（也可选第三方）
  - 夜间行车建议降低媒体音量

### 3.4 结果输出能力

**定义**：同时输出面向用户的自然语言回复和面向系统的结构化数据的能力。

#### 3.4.1 输出结构

每次 Agent 响应必须包含以下五个部分：

```json
{
  "user_response": "面向用户的自然语言回复（有温度、自然）",
  "service_plan": {
    "steps": ["结构化服务计划的步骤列表"],
    "tools_called": ["调用的工具列表及参数"],
    "estimated_time": "预估执行时间"
  },
  "reasoning": {
    "intent_analysis": "意图分析过程",
    "tool_selection_reason": "每个工具调用的选择理由",
    "alternatives_considered": "考虑过但未选择的替代方案"
  },
  "forbidden_actions": [
    {
      "action": "被禁止的动作",
      "reason": "禁止原因"
    }
  ],
  "safety_alerts": [
    {
      "level": "安全等级",
      "message": "安全提示信息"
    }
  ]
}
```

### 3.5 可体验呈现能力

**定义**：通过可访问的界面或 Demo 视频，让评委直观体验 Agent 能力。

- 提供可访问的 Web 链接或 Demo 视频
- 展示多个典型场景的完整处理流程
- 界面应体现 Agent 的思考过程和决策结果
- 支持交互演示（输入指令 → 观察 Agent 响应）

## 5. 八大标准场景详细拆解

### 5.1 场景一：疲劳驾驶提醒

**场景描述**：车主在长途驾驶过程中，系统检测到疲劳信号。

**输入信号**：
- 车辆状态：连续驾驶时长 > 2小时、当前车速、车道偏离次数增加
- 用户输入："我有点困" 或 无明显输入（系统主动检测）
- 环境信息：当前时间（深夜/午后）、路况（高速/城市）

**Agent 决策流程**：
```
检测疲劳信号
  → 评估疲劳等级（轻度/中度/重度）
  → 轻度：语音提醒 + 播放提神音乐 + 调低空调温度 + 开启座椅通风
  → 中度：上述 + 搜索最近服务区/休息站 + 建议导航前往
  → 重度：上述 + 强烈建议停车休息 + 如不响应则逐步减速靠边
  → 输出安全警告 + 拒绝继续长途导航（除非确认休息后）
```

**输出要求**：
- 用户回复："检测到您已连续驾驶2小时15分钟，建议您休息一会儿。我已为您找到前方3公里处的服务区，需要帮您导航过去吗？同时我帮您调低了些空调温度，播放一首轻快的音乐提提神。"
- 安全等级：L2（警告）
- 工具调用：`adjust_ac(-2°C)`, `set_seat_ventilation(on)`, `play_music(upbeat)`, `search_nearby(rest_area)`, `navigate_to(rest_area)`

### 5.2 场景二：亲子出行

**场景描述**：车主带着孩子（儿童/婴幼儿）出行。

**输入信号**：
- 用户输入："带着宝宝出门了" / "孩子好像在发烧" / 儿童座椅检测信号
- 车辆状态：后排座椅占用、儿童安全锁状态

**Agent 决策流程**：
```
识别亲子出行场景
  → 自动启用儿童安全模式（安全锁、车窗锁）
  → 调整后排空调温度和风量（避免直吹）
  → 推荐儿童适合的音频内容
  → 如果孩子不舒服：
      → 询问症状
      → 建议就近就医（搜索附近医院）
      → 必要时导航到最近医院
  → 持续监测后排状态
```

**安全红线**：
- 儿童在车内时，禁止关闭儿童安全锁
- 禁止将儿童单独留在车内（车辆熄火+驾驶员离座 → 告警）
- 后排温度不能过低/过高

### 5.3 场景三：长途补能

**场景描述**：长途自驾过程中需要充电/加油。

**输入信号**：
- 车辆状态：剩余电量/油量、当前续航、电池温度
- 用户输入："续航还够吗" / "帮我找个充电站" / 系统低电量预警
- 路线信息：目的地距离、沿途充电站分布

**Agent 决策流程**：
```
评估续航是否足够到达目的地
  → 足够：告知用户，建议途中备选充电站
  → 不够：
      → 搜索沿途充电站（优先小鹏自营）
      → 综合评估：距离、价格、空闲桩数、充电功率
      → 推荐最优充电站 + 理由
      → 导航到充电站
      → 到达后：自动开始充电（如支持）
      → 充电期间：推荐附近餐厅/休息区
      → 充电完成：继续导航到目的地
```

### 5.4 场景四：通勤到达前准备

**场景描述**：日常通勤场景，快到目的地时提前做好准备。

**输入信号**：
- 用户输入："快到公司了" / 接近导航目的地
- 车辆状态：距离目的地 < 1km
- 日程信息（可选）：会议时间、日历事件

**Agent 决策流程**：
```
检测到接近目的地
  → 搜索附近停车场
  → 推荐最优停车场（价格、距离、空位）
  → 导航到停车场
  → 到达前准备：
      → 提醒携带物品（手机、文件等）
      → 如有日程：提醒会议时间和地点
      → 关闭不必要的车载功能
  → 到达后：
      → 引导停车
      → 显示步行到目的地的路线
```

### 5.5 场景五：Robotaxi 找不到车

**场景描述**：乘客下单后，在约定上车点找不到车辆。

**输入信号**：
- 用户输入："我的车在哪" / "找不到车" / "车怎么还没来"
- 订单状态：司机已到达 / 车辆等待中
- 位置信息：乘客位置 vs 车辆位置

**Agent 决策流程**：
```
接收"找不到车"请求
  → 获取车辆实时位置
  → 计算乘客与车辆的距离
  → 远程触发车辆闪灯+鸣笛
  → 向乘客发送：
      → 车辆精确位置描述（"白色小鹏G6，在马路对面星巴克门口"）
      → 车牌号
      → AR导航/步行导航路线
  → 如果距离过远或位置不合理：
      → 建议修改上车点
      → 或重新派单
```

### 5.6 场景六：上车点异常

**场景描述**：Robotaxi 乘客的预设上车点存在问题。

**输入信号**：
- 环境信息：上车点施工、禁停、拥堵
- 用户输入："我在这里等你" （但位置在高速路上）
- 系统检测：上车点不安全/不合规

**Agent 决策流程**：
```
检测到上车点异常
  → 判断异常类型：
      → 道路施工 → 搜索附近替代上车点
      → 禁停区域 → 告知用户 + 推荐合规位置
      → 高速路/危险位置 → 拒绝 + 安全提醒 + 替代方案
      → 严重拥堵 → 建议改点 + 预估节省时间
  → 向乘客推荐替代上车点：
      → 距离原位置步行距离
      → 安全性评估
      → 预计节省时间
  → 乘客确认后更新订单
```

### 5.7 场景七：临时改目的地

**场景描述**：乘客/车主在行程中想要修改目的地。

**输入信号**：
- 用户输入："我想改去xxx" / "不去那里了，去yyy"
- 当前状态：已行驶距离、剩余距离、订单状态

**Agent 决策流程**：
```
接收改目的地请求
  → 评估可行性：
      → 新目的地是否在运营范围内（Robotaxi）
      → 预估新路线的费用和时间变化
      → 剩余续航是否足够
  → 向用户展示变更影响：
      → 新增费用 / 节省费用
      → 新增时间 / 节省时间
  → 用户确认后：
      → 更新导航路线
      → 更新订单信息（Robotaxi）
      → 如有需要，重新规划补能
```

### 5.8 场景八：乘客不适或求助

**场景描述**：Robotaxi 乘客在行程中感到身体不适或需要紧急帮助。

**输入信号**：
- 用户输入："我不太舒服" / "帮帮我" / "我要吐了" / SOS按钮
- 车辆传感器：异常体征检测（如有）

**Agent 决策流程**：
```
接收求助信号
  → 立即评估紧急程度：
      → 身体不适（非紧急）：
          → 询问症状
          → 调整空调（通风/降温）
          → 询问是否需要去医院
          → 如需要，导航到最近医院
      → 身体不适（紧急/疑似疾病发作）：
          → 立即安全停车
          → 呼叫120急救
          → 转接人工客服
          → 保持通话直到救援到达
      → 人身安全求助：
          → 立即安全停车
          → 报警（110）
          → 转接人工客服
          → 记录车内音视频（如允许）
      → 晕车/想吐：
          → 建议靠边停车
          → 打开车窗通风
          → 提供纸巾等物资位置信息
```

**安全红线**：
- 求助信号永远最高优先级，不可忽略
- 紧急情况下必须同时触发多重响应（停车+报警+转人工）

## 8. 安全规则与边界策略

### 8.1 安全规则清单

| ID | 规则名称 | 类型 | 触发条件 | Agent行为 |
|----|---------|------|---------|----------|
| S01 | 疲劳驾驶干预 | 硬 | 连续驾驶>2h 或 疲劳等级≥2 | 强制提醒+推荐休息点，等级≥3时限制继续驾驶 |
| S02 | 儿童安全保护 | 硬 | 儿童座椅检测到儿童 | 自动启用安全锁，禁止关闭 |
| S03 | 儿童遗留告警 | 硬 | 驾驶员离座+后排有儿童 | 立即告警+禁止锁车 |
| S04 | 乘客求助响应 | 硬 | 乘客发出求助信号 | 最高优先级响应，必要时转人工/报警 |
| S05 | 行驶中视觉限制 | 硬 | 车速>0 | 禁止播放视频、禁止弹出需长时间阅读的界面 |
| S06 | 高速车窗限制 | 硬 | 车速>80km/h | 禁止全开车窗，限制开窗幅度 |
| S07 | 充电安全 | 硬 | 充电中 | 禁止移动车辆，充电完成前限制部分功能 |
| S08 | 上车点安全校验 | 硬 | 创建/修改订单 | 高速路、施工区、禁停区拒绝作为上车点 |
| S09 | 紧急停车 | 硬 | L3/L4安全事件 | 寻找安全位置停车+呼叫救援 |
| S10 | 续航预警 | 软 | 剩余续航<目的地距离×1.2 | 主动提醒+推荐充电站 |
| S11 | 夜间噪音控制 | 软 | 22:00-06:00 | 建议降低媒体音量 |
| S12 | 温度舒适范围 | 软 | 空调设定温度 | 建议18-28°C范围 |

## 14. 风险评估与应对

| 风险 | 影响 | 概率 | 应对策略 |
|------|------|------|---------|
| LLM 响应不稳定 | Agent 输出质量波动 | 高 | 设置系统Prompt约束 + 输出格式校验 + Fallback逻辑 |
| 安全场景覆盖不全 | 评审扣分 | 中 | 建立安全规则清单 + 场景测试矩阵 |
| Demo 演示故障 | 评审体验差 | 中 | 录制备用视频 + 预置场景快速演示 |
| 场景理解过于简单 | 与竞品差距大 | 中 | 投入精力在Prompt工程和Few-shot示例 |
| 模拟数据不真实 | 体验感差 | 低 | 使用真实地图API数据 + 合理参数 |

## 附录 B：Prompt 工程要点

1. **系统 Prompt 应包含**：
   - Agent 角色定义（小鹏 AI 出行服务管家）
   - 可用工具列表及参数说明
   - 安全规则列表
   - 输出格式要求（JSON Schema）
   - 当前模式（车主/Robotaxi）

2. **用户 Prompt 应包含**：
   - 用户自然语言输入
   - 当前车辆状态快照
   - 当前环境信息
   - 用户画像摘要
   - 对话历史（最近N轮）

3. **Few-shot 示例**：
   - 至少为8个标准场景各准备1-2个 Few-shot 示例
   - 示例应覆盖显性/隐性/紧急三种意图类型
   - 示例应包含安全规则触发的情况
